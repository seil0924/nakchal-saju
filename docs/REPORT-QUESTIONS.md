# 구매한 리포트에 이어서 질문하기

## 동작

- 최초 결과와 보관함에서 다시 연 리포트 양쪽에서 이용합니다.
- 구매 권한을 서버에서 다시 검사합니다. 화면에서 보낸 본문·결제 레벨은 사용하지 않습니다.
- 서버가 현재 연도의 리포트를 다시 계산하고, 열람 가능한 항목만 AI에 보냅니다.
- 항목 선택, 추천 질문, 직접 질문, 최근 4문답을 이용한 후속 질문을 지원합니다.
- 답변의 근거는 실제 원문에 포함된 인용인지 검증합니다. 근거 버튼으로 항목을 펼칩니다.
- 날짜·리포트가 바뀌면 대화를 초기화합니다. 질문과 답변은 앱 DB·브라우저 저장소에 보관하지 않습니다.
- 생년월일·입력된 이름 등 알려진 식별정보를 발췌문과 질문에서 치환합니다. 자유 입력 속 개인정보를 완전히 탐지하는 기능은 아니므로 UI에서도 입력하지 않도록 알립니다.
- OpenAI 요청은 `store: false`입니다. 이는 제공자의 모든 로그 보관을 없앤다는 뜻이 아닙니다. 실제 계정의 데이터 처리 설정을 확인해야 합니다.

## 운영 연결

1. Supabase SQL Editor에서 `supabase/migrations/0012_report_questions.sql`을 적용합니다. 질문 내용 없이 요청 횟수만 보관합니다.
2. Vercel 프로젝트의 서버 환경변수에 `OPENAI_API_KEY`와 `REPORT_QA_MODEL`을 설정합니다. 모델은 계정에서 사용할 수 있으며 Responses API의 Structured Outputs를 지원해야 합니다. 키를 코드나 채팅에 적지 않습니다.
3. `REPORT_QA_ENABLED=true`로 설정하고 재배포합니다. 기존 Supabase 인증·서비스 역할 설정도 필요합니다.
4. 공개하기 전 실제 운영에 맞는 AI 데이터 처리 고지를 확인하고, 관리자용 가상 리포트에서 실제 모델 답변과 근거를 점검합니다. 설정 전에는 고객 화면에 질문 기능이 나타나지 않습니다.

환경변수는 런타임 검사입니다. `REPORT_QA_ENABLED=false` 후 재배포하면 즉시 새 AI 요청을 중단할 수 있습니다. 이미 열어둔 화면에서도 서버가 요청을 거절합니다.

## 한도와 장애

- 한국 날짜 기준 리포트당 하루 20회, 서비스 전체 하루 1,000회 요청입니다. RPC가 트랜잭션 안에서 원자적으로 검사하므로 서버 인스턴스가 달라도 합산합니다.
- 제공자에 요청을 보내기 직전에 횟수를 차감합니다. 제공자 오류·답변 검증 실패도 요청 횟수에 포함됩니다. 실패한 답변을 자동으로 재요청하지 않습니다.
- 카운터는 당일과 전날만 유지합니다(다음 요청 시 오래된 행 정리). 한도 변경은 SQL 함수와 `QA_DAILY_LIMIT`을 함께 수정합니다.
- SQL 미적용·DB 오류 시 외부 AI 호출을 차단합니다. 키 누락·활성화 미설정도 차단합니다.
- 제공자 요청 35초, 화면 요청 45초 제한. 질문은 오류 시 입력창에 남습니다.
- 미완성 응답·거절·잘못된 JSON·없는 근거는 성공 답변으로 표시하지 않습니다. 질문·토큰·리포트·제공자 오류 원문을 로그에 남기지 않습니다.

## 확인 항목

`npm test`와 `npm run build`. 추가로 휴대폰 화면에서 추천 질문, 동의, 답변 읽기, 원문 펼치기, 후속 질문, 제한·오류·구매 기록 복구를 점검합니다. 무료/타인 리포트, 잠긴 항목, 위조한 근거 요청은 서버가 차단해야 합니다.

외부 서비스 연결이 없는 테스트에서는 고정 응답을 사용합니다. 고정 응답은 실제 모델의 답변 품질 검증을 대신하지 않습니다.

공식 연동 참고: https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses
